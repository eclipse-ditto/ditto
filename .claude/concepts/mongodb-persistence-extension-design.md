# MongoDB persistence as an extension — design record

MongoDB is a drop-in persistence extension like PostgreSQL. Service main code has no MongoDB dependency; both
backends are shaded extension JARs that every Docker image ships in its own folder, `/opt/ditto/backends/<name>/`.
A fixed-name HOCON profile per backend carries the wiring, the environment variable `DITTO_PERSISTENCE_BACKEND`
(default `mongodb`) puts one folder on the classpath, and the persistence services refuse to start with zero or two
backends.

Related: `postgresql-persistence-design.md`, `context/persistence-backends.md`.

## Decisions

1. `internal/utils/persistence` (artifact `ditto-internal-utils-persistence`) stays as the MongoDB module and is not renamed. Neutral classes move out of it into `persistence-api`, including the `ReadPreference` and `ReadConcern` enums once their `com.mongodb` constants and `getMongo*()` accessors are replaced by a mapper in the Mongo module (`MongoReadSettings`); `MongoMetricsBuilder` moves *into* it from `metrics-service`.
2. Service modules declare `ditto-internal-utils-persistence-api` at compile scope and have no MongoDB dependency in main code; the Mongo modules are test-scope dependencies only. The shaded allinone JARs therefore carry no backend: a service gets one from `/opt/ditto/backends/` in the image, or from the `ide-mongo-launcher` / `ide-postgres-launcher` modules in IntelliJ.
3. Event adapters: one neutral `EventSerializer` subclass per entity stays in the service; each backend module holds a generic delegating Pekko adapter plus one thin subclass per entity in a *backend package*: `org.eclipse.ditto.internal.utils.persistence.mongo.adapters` and `org.eclipse.ditto.internal.utils.persistence.postgres.adapters`. The shipped class-name strings in the service confs, the PostgreSQL profile and the test confs are updated. No split packages: the service ArchUnit tests import by package across the whole test classpath, so adapters that kept service packages would fail the boundary rules.
4. `AbstractPolicyMongoEventAdapter` is deleted; `DefaultPolicyMongoEventAdapter` is the single thin policies adapter (name kept as decided; the `Default` prefix is historical). `PolicyEventSerializer` is non-final and is the extension point: subclass it and write a one-line adapter naming it.
5. The Mongo search code moves to a new module `thingsearch/persistence-mongo` (artifact `ditto-thingsearch-persistence-mongo`, root package `org.eclipse.ditto.thingsearch.persistence.mongo`, provider at the root, sub-packages `config`, `read`, `write`) with no dependency on `thingsearch/service`. The default of `ditto.extensions.search-persistence-provider` becomes the moved class name; this is a release-note item, no alias class.
6. Pre-actor-system config (the Mongo URI injection) goes through a `ServiceLoader` SPI, `PersistenceBackendBootstrap`. The Mongo bootstrap injects the URI whenever `ditto.mongodb` is present; the search service also receives the key (harmless, it starts no Pekko journal).
7. Image layout: `/opt/ditto/backends/mongodb/`, `/opt/ditto/backends/postgresql/`; `/opt/ditto/extensions/` stays for user JARs. Selector: env `DITTO_PERSISTENCE_BACKEND`, default `mongodb`, value = folder name.
8. Each backend ships two fixed-name wrapper profiles, `ditto-persistence-backend.conf` and `ditto-search-backend.conf`, each a one-line include of that backend's uniquely named profile (`ditto-mongo-persistence.conf`, `ditto-mongo-search.conf`, `ditto-postgres-persistence.conf`, `ditto-postgres-search.conf`). Service confs include the fixed name at top level, *not* `required`, so a missing backend fails in the boot check (Decision 11) with a clear message rather than in config loading. A profile declares per-entity auto-start lists under its own namespace, `ditto.persistence-backend.auto-start.<entity>.{journals,snapshots}`, and each service conf assigns its own by optional static substitution over an empty default. The PostgreSQL profile gets the same keys and loses its all-four-entity default lists. While two backends share a classpath (the search-r2dbc test classpath) Typesafe Config merges every same-named classpath resource, so the fixed-name include loads both profiles; an overlay or test then selects one by including the unique name, which wins because `RawConfigSupplier` layers the environment file above the service conf. No narrowing overlay exists any more. Connectivity's remember-store plugin ids are not profile keys: `ConnectivityRootActor` takes them from the provider's plugin config for both backends; the two static lines in `connectivity.conf` are inert defaults. The `collection-cache` blocks in `things.conf` and `policies.conf` differ from each other and stay inline (inert on PostgreSQL).
9. Two Mongo extension JARs: the fat `ditto-mongo-persistence-extension` (client, driver, Pekko plugin, provider, adapters, profiles) and the thin `ditto-mongo-search-extension`. Trade-off accepted: the search image carries the Pekko journal plugin and the adapters it never uses, and the thin JAR needs the fat one. A pairing self-check with version markers (like the PostgreSQL one) enforces that.
10. IntelliJ: new `ide-mongo-launcher` module; the four default service `.run/*.run.xml` point at it. `Ditto.run.xml` is a compound configuration and is not touched.
11. The exactly-one-backend check runs in `DittoService.doStart()` before the actor system exists, gated by `protected boolean requiresPersistenceBackend()` (default `false`; things, policies, connectivity and search return `true`), counting distinct backend names. The PostgreSQL bootstrap ships in `postgres-client`, the base JAR every PostgreSQL image carries. No secondary check in `PersistenceBackendProvider.get`.
12. A PostgreSQL deployment that still stages its JARs into `/opt/ditto/extensions/` without `DITTO_PERSISTENCE_BACKEND=postgresql` has two backends and is refused at boot with a message naming the fix. Accepted and announced (Helm CHANGELOG, docs); no auto-detection in the entrypoint.
13. `ditto-mongo.conf` (the `ditto.mongodb.*` defaults with their `MONGO_DB_*` overrides) moves from `internal/utils/config` into the Mongo module and is included by both Mongo profiles (`ditto-mongo-persistence.conf`, `ditto-mongo-search.conf`), as the PostgreSQL profiles include `ditto-postgres-client.conf`. `ditto-service-base.conf` drops the include. The `pekko.contrib.persistence.mongodb.mongo` block of `ditto-pekko-config.conf` moves into `ditto-mongo-persistence.conf` (only the Pekko plugin reads it; the search service's main code uses no `MongoReadJournal` and no Pekko journal). The four `${ditto.mongodb.options.readPreference|readConcern}` substitutions in `search.conf` become optional substitutions over a literal default equal to the former value, so the file resolves on PostgreSQL. The lines stay in `search.conf` instead of moving into the Mongo search profile, because `SearchPersistenceConfig.readPreference()` stays on neutral code (Decision 15), so the key must resolve on both backends; the resolved values are identical (`ditto-mongo.conf` ships `primary` / `local`) and the `QUERY_` / `UPDATER_PERSISTENCE_MONGO_DB_READ_*` overrides keep working. The inline per-service `ditto.mongodb { database = ... }` blocks stay where they are: they are per-service values of keys only the Mongo backend reads.
14. `SearchPersistenceConfig`, `DefaultSearchPersistenceConfig`, `PersistenceStreamConfig` and `DefaultPersistenceStreamConfig` move to `thingsearch/persistence-api` (package `org.eclipse.ditto.thingsearch.persistence.api.config`) after the Mongo `WriteConcern` getter leaves `PersistenceStreamConfig`. The Mongo module reads its own configuration from the raw actor-system `Config` through `MongoSearchConfig`, as the PostgreSQL provider already does, and never sees `SearchConfig`.
15. `SearchConfig` keeps `getSimpleFieldMappings()` and `SearchPersistenceConfig` keeps `readPreference()`/`readConcern()`: neutral service code (`SearchRootActor`, `OperatorMetricsProviderActor`) calls them.
